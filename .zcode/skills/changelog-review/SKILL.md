# Skill: changelog-review——CHANGELOG 用户视角评审总结

## 定位

发版记账前的文案环节：把 CHANGELOG.md 当版小节（`## [未发布]`；已版本化则最新 `## [x.y.z]`）从实现者视角提炼为用户视角——用户能看到什么、能得到什么、要留意什么。只改措辞与详略：不增删功能点、不改事实、不改 Keep a Changelog 分类体系。

## 用户视角判据（逐条过）

1. **一句话主旨优先**：每条变更先写一句话 takeaway——写得出一句话的就一句话收掉（如整段设置页改版细节 → 「优化设置页的显示效果」）；只有对用户可操作的细节（去哪开、怎么配、何时注意）才保留为短列表。
2. **删工程内部**：实现机制（指令编译 / 接口字段 / 架构调整）、验证依据（真机验证 / 测试证据）、过程叙述（返修轮次 / 此前行为 / 后续规划）不出现在正文——留痕归 Issue / ROADMAP / DESIGN。
3. **保留可操作信息**：新能力入口与用法要点、限制与坑（不支持的场景、须一致的配置）、升级注意（行为 / 数据变化）——用户要据此行动的不能丢。
4. **措辞与既有 CHANGELOG 一致**：中文；条目加粗主语开头；分类用 新增 / 改进 / 修复 / 升级注意（条目归类可按用户视角修正）；不出现公司 / 业务线品牌字样；不出现过程标记（迭代号 / 决策号 / Issue / PR 引用）。
5. **不虚构不夸大**：提炼只做压缩与视角转换；功能范围、适用条件、限制与原文一致，拿不准的限制宁可保留。

## 流程

1. **定位**：CHANGELOG.md 当版小节（`## [未发布]` 优先，无则最新 `## [x.y.z]`）；历史版本小节与 0.x 速览不动；小节为空时说明并停止。
2. **分类**：逐条标记——用户可感知（保留提炼）/ 工程内部（删或并入一句话）/ 可操作细节（收敛为子列表）。
3. **候选稿**：改写工作区 CHANGELOG.md 当版小节（**不提交**）；同时准备「逐条 原→新 一行对照 + 删除项及去向」摘要。
4. **确认**：候选稿全文＋对照摘要展示给用户——确认前不提交。通过 → 修订随发版记账 PR 或小 PR 提交；不通过 → 按反馈返修，或 `git checkout -- CHANGELOG.md` 复原、经验回写本技能。
5. **联动**：Release 正文自动取当版小节（release.yml 提取步骤），确认后的措辞随下次发版自然呈现，无需单独同步。

## 边界

- 只处理 CHANGELOG.md 当版小节；已发布版本的既有小节措辞按用户指示单独处理，不主动翻旧账。
- 技能产出是「候选稿＋对照」，不是最终裁决——用户确认才是。
